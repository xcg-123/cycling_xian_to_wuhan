# 下一阶段执行方案

## 当前可交付与缺口
已交付七份研究文档、公开源访问日志、官方软件文档快照、本地分析脚本及测试。未取得真实道路轨迹、DEM、气象观测、行者导入导出结果或完整可执行走廊。这些是明确缺口，不用模拟 GPX 填补。

## 顺序与验收
1. **解除取数前置条件**：在环境设置按 `data/network_requirements.json` 增加需要的域名，保留已有规则。先高德文档/接口、OSM/Overpass、行者官网，再按实际产品添加高程和气象域名。不盲目放行通配符；重定向新域名再核查。Key 安全注入，确认 Web 服务类别和骑行服务权限。代理放行不等于源站授权。
2. **短段端到端实验**：用户明确校门后，选 2—5 km 普通道路测试段，再选含桥/隧道风险的山口样段。对高德记录请求模式、业务状态、paths、步行推车信息（如提供）、距离和几何；对 OSM 记录数据时间和缺失标签。长度仅是实验设计，不是已证实 API 上限。失败先分类网络、鉴权、配额、距离、无路可达，禁止用驾车结果替代。
3. **行者往返实验**：官方登录→创建可分享测试路线或导入合法短轨迹→导出→比较点数、分段、航点、坐标与海拔→设备离线跟随。记录 App/网页版本、账号级别和 UI 路径。先测试非敏感轨迹，未成功前不把行者列为唯一交付渠道。
4. **A/B 同口径取数**：固定起终点、关键普通道路控制点和禁行规则，按服务实际限额分段；保存原始响应并审计拼接。统计距离、未知路面、桥隧和关键缺口；先处理可能一票否决的山口/过江，避免浪费大量算路。
5. **地形和季节分析**：获取有许可、覆盖完整的 DEM；记录版本、CRS、垂直基准、NoData，比较多窗口坡度和累计爬升。隧道/桥面特殊处理。取沿线气象站多年同期资料，分析湿热和强降雨，不把历史均值当 2027 预报。
6. **实证闭环**：查主管部门和交警公告，必要时由用户联系地方管理单位/近期骑友核查重点段。本阶段没有擅自联系任何人。照片、通行说明必须记录时间、方向和车辆类型。
7. **阶段二验收**：至少两条具有连续真实道路几何的候选，全部关键桥隧/山口风险已有证据或可执行绕行，距离/高程/未知路面有来源，候选在同样规则下比较。若仅一条通过，明确一条，不凑数。
